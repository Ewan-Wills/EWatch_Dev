# Claude Face — always-on Claude Code tracker for EWatch

Status (2026-09-30): the watch firmware is now **stand-alone**: `ClaudeFace/firmware/` is a PlatformIO project of its own that is only this face (no launcher, other faces, WiFi or sleep). AuroraOS no longer contains the Claude face. The stand-alone build is host-tested but not yet flashed; the AuroraOS-hosted build described below (2026-09-23) is what ran on the watch until then.

Earlier status (2026-09-23): **flashed and running on Ewan's watch** with live data from his Claude Code sessions (bridge under launchd, hooks + statusline installed). Firmware built with `EW_NO_SLEEP=1`: no sleep at all, the LDO latch is driven high at boot and pad-held (`gpio_hold_en`) so it can't float low through a reset. Only the 3 s side-button hold releases it. Verified 2026-09-23: an esptool chip reset with no button held no longer powers the watch off, so flashing works hands-free.

## Architecture

```

            ──statusline (tee, bg curl)┤
                                       ▼
                 claude-bridge (Node, 127.0.0.1:7337)
```

## Transport: USB serial instead of BLE

Per Ewan's instruction the link is USB-C serial, not BLE. Consequences:

- No NimBLE / noble / bleak, no pairing or bonding (a cable is its own authentication), no RSSI or range figures.
- Frames are text lines so they coexist with the firmware's log lines and its small `cf` console on the same CDC port (one mutex around every Serial write, so a log line never lands inside a frame). Any line starting `#CF` belongs to the protocol; everything else is a log line, which the bridge appends to `~/Library/Logs/claude-bridge-watch.log`.
- The watch appears as `/dev/cu.usbmodem*` (Espressif USB-Serial-JTAG, VID 0x303A). The bridge finds it by sending `#CFQ` and waiting for a `#CFH` HELLO.
- **Only one program can hold the port.** Before `pio run -t upload` or `pio device monitor`, run `curl -X POST '127.0.0.1:7337/serial/release?seconds=120'`.
- Being "connected" also means the cable is in, so the watch is **charging** whenever the face is in always-on mode. Battery drain in connected mode is therefore not a meaningful number. The stand-alone firmware never sleeps, so off the cable it runs the screen at the ambient level until the battery is flat or the side button is held 3 s.
- The bridge opens the port with `hupcl:false` and never toggles DTR/RTS. On the S3's USB-Serial-JTAG some RTS/DTR sequences reset the chip. **Check on first connect that opening the port does not reboot the watch** (`uptime_s` in `cf stats`).

## State machine (bridge)

| Input | Effect |
|---|---|
| SessionStart | create → IDLE |
| UserPromptSubmit | WORKING, turn start, clear unacked DONE |
| PreToolUse | WORKING, current_tool = `Tool\|target` (Bash: first 24 chars of first line; Edit/Write/Read/NotebookEdit: basename; others: name) |
| PostToolUse / PostToolUseFailure | WORKING, tool count++ |
| PermissionRequest | BLOCKED immediately, current_tool = the requested tool |
| Notification permission_prompt / elicitation_* | BLOCKED (backup; fires only after ~6 s without typing) |
| Notification idle_prompt / agent_needs_input | WAITING_INPUT |
| Notification quota_auto_resume_fired | clear LIMITED |
| PermissionDenied | back to WORKING (or IDLE) |
| Stop | DONE (unacked), record turn duration |
| StopFailure error=rate_limit / billing_error / account_on_hold | LIMITED |
| StopFailure, other errors | DONE |
| SubagentStart / SubagentStop | subagent count ± |
| PreCompact / PostCompact | COMPACTING / back to the previous state |
| SessionEnd | remove |
| any window ≥ 100 % | LIMITED |
| no event 10 min, not WORKING | STALE; stale > 1 h → removed |
| WORKING, no event 10 min | `quiet` / HUNG flag |

Global priority: BLOCKED > LIMITED > WAITING_INPUT > WORKING > COMPACTING > DONE (unacked) > IDLE > NONE.
Primary session: first BLOCKED, else most recent activity. The watch can override it with SELECT_SESSION, which holds until that session ends.

## Known gaps (shown in the UI, not hidden)

- claude.ai web/desktop/mobile chats have no hooks. They show only through the shared 5h/7d percentages.
- Rate-limit % is only as fresh as the last Claude Code API response. `rl_age_s` is sent, and after 15 min the rings are drawn dimmed (a dimmed fill instead of hollow: a hollow outline shows a seam where the arc splits at 12 o'clock).
- API-key sessions never get `rate_limits`. The `NO_RATE_LIMITS` flag makes the rings show "—", never 0 %.
- `permission_prompt` notifications only fire after ~6 s idle, so PermissionRequest is the primary BLOCKED trigger.
- `idle_prompt` is not sent while Claude Code waits on a usage-limit reset.
- **Desktop-app (Code tab) sessions don't run the statusline**, so they are filled from other sources:
  - model and context % come from the tail of each session's transcript (`transcript_path` from the hooks; only token counts and the model id are read). The window is 1M if the model id says `[1m]` or the context is already > 200k, else 200k.
  - the project name is the git root of the session's directory.
  - 5h/7d usage comes from the **undocumented** OAuth usage endpoint (`api.anthropic.com/api/oauth/usage`), polled every 5 min with Claude Code's own token read from the Keychain (item `Claude Code-credentials`; never refreshed, stored or logged). Enabled by Ewan 2026-09-23 in `~/.config/claude-bridge/config.json` → `oauthUsage.enabled`. If it breaks, the rings age into stale/"—".
  - cost, lines ± and PR state stay "—" for these sessions (statusline-only fields).
- The status page poller is off by default.

## Where this differs from the original prompt

See `docs/docs-verification.md` for the full docs check. In short:
1. **Transport**: serial, not BLE (Ewan's instruction). No pairing, RSSI or range; "connected" means cable in, so the watch is charging.
2. **Firmware target**: first AuroraOS (the unified firmware that grew out of BaseOS). Since 2026-09-30 it is its own stand-alone firmware in `ClaudeFace/firmware/` (Ewan: AuroraOS should be its own thing), built on the same pins as AuroraOS / HeadFace (espressif32@6.13.0, arduino-esp32 2.0.17).
3. **API-error hook**: `StopFailure`. Only `rate_limit` (plus billing/account-hold) maps to LIMITED; overloaded/server errors don't.
4. **Extra hooks the prompt didn't list**, now handled: PostToolUseFailure, PermissionDenied, PostCompact, and more Notification types.
5. **PermissionRequest** is the fast BLOCKED path, not `Notification(permission_prompt)`, which lags ~6 s.
6. **Hooks run with `"async": true`**, so they can never slow Claude down.
7. **Swipe left/right** cycles sessions anywhere on the face (the stand-alone firmware has no other faces to swipe to).
8. **current_tool separator** is sent as `|`. The landscape face shows the tool and its target on two lines; elsewhere `|` is drawn as a middle dot (the fonts are ASCII-only). "—" is drawn as a bar.
9. **Landscape** (Ewan, 2026-09-23): the watch sits on its side at the desk, plugged into USB-C, so the Claude face is drawn 280×240 landscape instead of the SPEC's 240×280 portrait. See "Landscape" below.

## Landscape

The Claude face reads upright when the watch's physical **top edge points right** (native panel row y = 0 on the right).

- Mapping: viewer (vx, vy) on the 280×240 canvas ↔ panel (px, py) = (vy, 279 − vx). This is `Arduino_Canvas` rotation 3. All of it lives in `ClaudeFace/firmware/src/cf_orient.h`.
- The face sets the full-frame PSRAM canvas to rotation 3 **only for the length of each draw call**, then puts it back to 0. The framebuffer is always the native portrait image, so `flush()` sends it as is. A dirty logical region is pushed as its panel rect through a centre-disc-sized scratch buffer, in bands of rows.
- Layout: rings on the left (136 px column, ring radius 64), HH:MM top right with link glyph and battery under it, activity block below that (project, large turn timer, tool on two lines in JetBrains Mono, ctx % + subagent dots, context bar), reset / projected-hit caption under the rings as a small label with a large value, and the footer across the full width (other-session pills, "+N", "cache cold in 3m").
- Detail page (long press) is landscape too: one row per field, label left, value right.

Input on the stand-alone firmware (touch points and CST816S swipe directions arrive in native portrait terms and are converted first; chip ids use AuroraOS' names):

| Chip gesture | Viewer swipe | Action |
|---|---|---|
| 0x03 SwipeLeft | up | open the detail page |
| 0x04 SwipeRight | down | nothing |
| 0x01 SwipeDown | left | next session (SELECT_SESSION) |
| 0x02 SwipeUp | right | previous session |
| any swipe with the detail page open | | closes it |
| tap | | ACK when the primary is DONE (unacked) or anything is BLOCKED; closes the detail page if open |
| long press (0.7 s) | | detail page on / off (closes itself after 30 s) |
| side button, short press (< 1 s) | | detail page on / off |
| side button, hold 3 s | | power off (on USB: dark until SW2 is held 1 s, then restart) |

Session swipes need a live bridge and at least two sessions. The AuroraOS-hosted version had a session zone (activity block + footer) because swipes elsewhere changed face, and swipe up / down / the side button went to AuroraOS' launcher and control centre; none of that exists here.

## Phase 2 hooks already in the design

- EVENT codes APPROVE=16 / DENY=17 are reserved. A blocking PermissionRequest hook would long-poll `/permission/<id>` on the bridge and fall through on timeout. Never auto-approve; the per-tool allowlist defaults to empty.
- The `INCIDENT` flag bit already exists (status-page poller, off by default).
- A History page can be fed from `~/.claude/projects/**/*.jsonl` by the bridge. The protocol has room: STATE is 119 of the 180-byte budget.

## Flashing with the bridge running

```sh
launchctl bootout gui/$(id -u)/com.ewills.claude-bridge                                   # frees the USB port
cd ClaudeFace/firmware && ~/.platformio/penv/bin/pio run -t upload
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.ewills.claude-bridge.plist
```
Firmware older than the latch-hold build switches off during a flash unless the side button is held. Going back to AuroraOS is the same with `cd AuroraOS`.

## First flash (Ewan's step) and on-hardware checks

```sh
cd ClaudeFace/firmware && ~/.platformio/penv/bin/pio run -t upload # build + flash over USB-C
~/.platformio/penv/bin/pio device monitor                           # type: cf stats   (then Ctrl-C)
cd ../bridge && npm install && npm run build
node dist/src/cli.js simulate --speed 1                             # watch the face walk every state
node dist/src/cli.js                                                # real bridge (foreground)
../claude-config/install.sh                                         # hooks + statusline (backs up settings.json)
scripts/install-launchd.sh                                          # autostart, when happy
```

Check in this order. Each item is untested on hardware with the stand-alone firmware:
1. Opening the port (bridge or simulate) does **not** reboot the watch (RTS/DTR). `cf stats` uptime keeps counting.
2. `cf stats` shows frames ok and bad = 0 under simulator traffic (1 KB RX buffer, 10 ms link-task poll).
3. Landscape: with the watch's top edge pointing right the face reads upright. Swipe left / right = next / previous session, swipe up = detail page, tap = ACK, long press or a short button press = detail page, 3 s button hold = off. (Assumes AuroraOS' names for the CST816S gesture ids match finger travel on the panel, as its portrait UI relies on.)
4. No visible flicker with the WORKING spinner (70 ms frames; the stand-alone firmware runs at 240 MHz).
5. Haptic feel: `cf buzz blocked|done|cross|reset`.
6. Event → pixel latency: run the bridge with `--trace`, submit a prompt, film the watch next to the terminal. Budget is ≈ 250 ms debounce + ≤ 10 ms link poll + ≤ 10 ms UI loop + one render.
7. Power: hold the side button 3 s on battery and the watch is off; on USB it goes dark and a 1 s hold restarts it. Holding the button a little long at power-on must not turn it straight back off.
