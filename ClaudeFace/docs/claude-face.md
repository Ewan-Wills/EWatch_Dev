# Claude Face — always-on Claude Code tracker for EWatch

Status (2026-09-23): **flashed and running on Ewan's watch** with live data from his Claude Code sessions (bridge under launchd, hooks + statusline installed). Firmware built with `EW_NO_SLEEP=1`: no sleep at all, the LDO latch is driven high at boot and pad-held (`gpio_hold_en`) so it can't float low through a reset. Only the 3 s side-button hold releases it. Verified 2026-09-23: an esptool chip reset with no button held no longer powers the watch off, so flashing works hands-free.

## Architecture

```
Claude Code ──hooks (async, curl -m1)──┐
            ──statusline (tee, bg curl)┤
                                       ▼
                 claude-bridge (Node, 127.0.0.1:7337)
                 session table · state machine · rate-limit cache
                 pace / projected-hit · debounce 250 ms · heartbeat 30 s
                                       │  USB-C, CDC serial text lines
                                       ▼  #CF<type> <base64(payload‖crc16)>
                 EWatch · AuroraOS
                 ewlog console task → cf_link (double-buffered snapshot)
                 render task → Claude face (dirty regions) · haptics · power hold
```

## Transport: USB serial instead of BLE

Per Ewan's instruction the link is USB-C serial, not BLE. Consequences:

- No NimBLE / noble / bleak, no pairing or bonding (a cable is its own authentication), no RSSI or range figures.
- Frames are text lines so they coexist with AuroraOS log output and the `ewlog` console on the same CDC port. Any line starting `#CF` belongs to the protocol; everything else is a log line, which the bridge appends to `~/Library/Logs/claude-bridge-watch.log`.
- The watch appears as `/dev/cu.usbmodem*` (Espressif USB-Serial-JTAG, VID 0x303A). The bridge finds it by sending `#CFQ` and waiting for a `#CFH` HELLO.
- **Only one program can hold the port.** Before `pio run -t upload` or `pio device monitor`, run `curl -X POST '127.0.0.1:7337/serial/release?seconds=120'`.
- Being "connected" also means the cable is in, so the watch is **charging** whenever the face is in always-on mode. Battery drain in connected mode is therefore not a meaningful number. The drain that matters is the disconnected, normal-AuroraOS mode.
- The bridge opens the port with `hupcl:false` and never toggles DTR/RTS. On the S3's USB-Serial-JTAG some RTS/DTR sequences reset the chip. **Check on first connect that opening the port does not reboot the watch** (watch uptime in `cf stats` / `pwr stats`).

## State machine (bridge)

| Input | Effect |
|---|---|
| SessionStart | create → IDLE |
| UserPromptSubmit | WORKING, turn start, clear unacked DONE |
| PreToolUse | WORKING, current_tool = `Tool\|target` (Bash: first 24 chars of first line; Edit/Write/Read/NotebookEdit: basename; others: name) |
| PostToolUse / PostToolUseFailure | WORKING, tool count++ |
| PermissionRequest | BLOCKED immediately, current_tool = the requested tool |
| Notification permission_prompt / elicitation_* | BLOCKED (backup; fires only after ~6 s without typing) |
| Notification idle_prompt / agent_needs_input | WAITING_INPUT |
| Notification quota_auto_resume_fired | clear LIMITED |
| PermissionDenied | back to WORKING (or IDLE) |
| Stop | DONE (unacked), record turn duration |
| StopFailure error=rate_limit / billing_error / account_on_hold | LIMITED |
| StopFailure, other errors | DONE |
| SubagentStart / SubagentStop | subagent count ± |
| PreCompact / PostCompact | COMPACTING / back to the previous state |
| SessionEnd | remove |
| any window ≥ 100 % | LIMITED |
| no event 10 min, not WORKING | STALE; stale > 1 h → removed |
| WORKING, no event 10 min | `quiet` / HUNG flag |

Global priority: BLOCKED > LIMITED > WAITING_INPUT > WORKING > COMPACTING > DONE (unacked) > IDLE > NONE.
Primary session: first BLOCKED, else most recent activity. The watch can override it with SELECT_SESSION, which holds until that session ends.

## Known gaps (shown in the UI, not hidden)

- claude.ai web/desktop/mobile chats have no hooks. They show only through the shared 5h/7d percentages.
- Rate-limit % is only as fresh as the last Claude Code API response. `rl_age_s` is sent, and after 15 min the rings are drawn dimmed (a dimmed fill instead of hollow: a hollow outline shows a seam where the arc splits at 12 o'clock).
- API-key sessions never get `rate_limits`. The `NO_RATE_LIMITS` flag makes the rings show "—", never 0 %.
- `permission_prompt` notifications only fire after ~6 s idle, so PermissionRequest is the primary BLOCKED trigger.
- `idle_prompt` is not sent while Claude Code waits on a usage-limit reset.
- **Desktop-app (Code tab) sessions don't run the statusline**, so they are filled from other sources:
  - model and context % come from the tail of each session's transcript (`transcript_path` from the hooks; only token counts and the model id are read). The window is 1M if the model id says `[1m]` or the context is already > 200k, else 200k.
  - the project name is the git root of the session's directory.
  - 5h/7d usage comes from the **undocumented** OAuth usage endpoint (`api.anthropic.com/api/oauth/usage`), polled every 5 min with Claude Code's own token read from the Keychain (item `Claude Code-credentials`; never refreshed, stored or logged). Enabled by Ewan 2026-09-23 in `~/.config/claude-bridge/config.json` → `oauthUsage.enabled`. If it breaks, the rings age into stale/"—".
  - cost, lines ± and PR state stay "—" for these sessions (statusline-only fields).
- The status page poller is off by default.

## Where this differs from the original prompt

See `docs/docs-verification.md` for the full docs check. In short:
1. **Transport**: serial, not BLE (Ewan's instruction). No pairing, RSSI or range; "connected" means cable in, so the watch is charging.
2. **Firmware target**: AuroraOS, the current unified firmware that grew out of BaseOS. BaseOS is the older bare slate, lacks the Aug-29 warm-reset crash-loop fix, and has an unpinned platform that resolves to arduino-esp32 v3 on this Mac.
3. **API-error hook**: `StopFailure`. Only `rate_limit` (plus billing/account-hold) maps to LIMITED; overloaded/server errors don't.
4. **Extra hooks the prompt didn't list**, now handled: PostToolUseFailure, PermissionDenied, PostCompact, and more Notification types.
5. **PermissionRequest** is the fast BLOCKED path, not `Notification(permission_prompt)`, which lags ~6 s.
6. **Hooks run with `"async": true`**, so they can never slow Claude down.
7. **Swipe left/right** already cycles faces in AuroraOS. On the Claude face, swipes that start in the lower part (activity strip/footer) cycle sessions; swipes higher up still cycle faces.
8. **current_tool separator** is sent as `|` and drawn as a middle dot (the fonts are ASCII-only). "—" is drawn as a bar.

## Phase 2 hooks already in the design

- EVENT codes APPROVE=16 / DENY=17 are reserved. A blocking PermissionRequest hook would long-poll `/permission/<id>` on the bridge and fall through on timeout. Never auto-approve; the per-tool allowlist defaults to empty.
- The `INCIDENT` flag bit already exists (status-page poller, off by default).
- A History page can be fed from `~/.claude/projects/**/*.jsonl` by the bridge. The protocol has room: STATE is 119 of the 180-byte budget.

## Flashing with the bridge running

```sh
launchctl unload ~/Library/LaunchAgents/com.ewills.claude-bridge.plist   # frees the USB port
cd AuroraOS && ~/.platformio/penv/bin/pio run -t upload
launchctl load ~/Library/LaunchAgents/com.ewills.claude-bridge.plist
```
Firmware older than the latch-hold build switches off during a flash unless the side button is held.

## First flash (Ewan's step) and on-hardware checks

```sh
cd AuroraOS && ~/.platformio/penv/bin/pio run -t upload            # build + flash over USB-C
~/.platformio/penv/bin/pio device monitor                           # type: cf stats   (then Ctrl-C)
cd ../ClaudeFace/bridge && npm install && npm run build
node dist/src/cli.js simulate --speed 1                             # watch the face walk every state
node dist/src/cli.js                                                # real bridge (foreground)
../claude-config/install.sh                                         # hooks + statusline (backs up settings.json)
scripts/install-launchd.sh                                          # autostart, when happy
```

Check in this order. Each item is untested on hardware:
1. Opening the port (bridge or simulate) does **not** reboot the watch (RTS/DTR). `cf stats` uptime keeps counting.
2. `cf stats` shows frames ok and bad = 0 under simulator traffic (1 KB RX buffer, 50 ms console poll).
3. Swipe zones: a swipe starting in the lower third changes session, a higher one changes face, and the side button still goes back.
4. No visible flicker with the WORKING spinner (70 ms frames at 80 MHz; if it stutters, drop `frameMs` to ≤ 66 so the CPU goes to 240 MHz).
5. Haptic feel: `cf buzz blocked|done|cross|reset`.
6. Event → pixel latency: run the bridge with `--trace`, submit a prompt, film the watch next to the terminal. Budget is ≈ 250 ms debounce + ≤ 50 ms console poll + one render.
7. Battery: drain in disconnected mode with `pwr stats` over a couple of hours. Connected mode is on USB power, so there is no drain to measure.
